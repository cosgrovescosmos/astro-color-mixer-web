Astro Color Mixer Web Technical Appendix

Processing assumptions, Selected Band mask model, Range Mask model, and browser-side implementation notes.

1. Introduction

This appendix describes the processing model used by Astro Color Mixer Web and the practical assumptions behind it. The tool is designed for nonlinear RGB astrophotography images and combines hue-band selection, luminance-range masking, low-saturation handling, and sequential refinement passes.

The goal is not to claim physically perfect color reconstruction. The goal is to provide a controlled nonlinear RGB editing model that is useful for astrophotography finishing work in a browser-based environment.

2. Design Goals

  • controlled nonlinear RGB refinement
  • an astro-specific color-band workflow
  • prevention of arbitrary global color swings
  • support for both stars-present and starless workflows
  • visible mask and diagnostic feedback
  • client-side processing without uploading image data to a server

This makes the tool a finishing and refinement environment rather than a calibration or reconstruction framework.

3. Processing Assumptions

  • nonlinear RGB input
  • normalized floating-point RGB values in the range 0..1
  • browser-local image data processing
  • preview uses downsampled data for responsiveness
  • final save uses full-resolution working data

These assumptions matter because the tool is intended for post-stretch, visually guided adjustment.

4. Image Type: Stars Present vs Starless / Star-Reduced

In Stars Present mode, Astro Color Mixer Web assumes the image still contains bright stellar structures, star cores, and halos. Protection is more conservative around bright star-like regions so large color or luminance moves are less likely to produce star-core distortion, oversaturated halos, or harsh highlight artifacts.

In Starless / Star-Reduced mode, Astro Color Mixer Web assumes stars have already been removed or strongly reduced. Protection can therefore allow more freedom in nebulae, galaxies, dust, and faint structures.

This setting does not detect stars, remove stars, or create a star mask. It changes protection weighting conceptually during adjustment.

5. Luminance Model

Y = 0.2126 R + 0.7152 G + 0.0722 B

Luminance is used for Range Mask construction, preview diagnostics, Neutral / Low-Saturation luminance control, and dark/highlight protection.

6. Hue and Saturation Selection

Hue and saturation are used for selection and adjustment behavior in an HSL-style sense. Hue is circular, hue distance must wrap at the ends of the angle domain, and low saturation makes hue unreliable.

This is why weak-color background, dust, and gray structures use a separate low-saturation path instead of relying on raw hue angle alone.

7. Astro Color Bands

red 0°
orange 30°
yellow 60°
green 120°
cyan 180°
blue 240°
purple 275°
magenta 315°

These band centers are practical editing regions, not strict physical line definitions.

8. Hue Radius and Feather

The Selected Band control in the current web engine is best understood as an outer angular radius on each side of the hue center.

distance = circularHueDistance(hue, center)
outerWidth = width
innerWidth = width * (1 - feather)
mask = 1 - smoothstep(innerWidth, outerWidth, distance)

This creates three distinct states:

  • Strong core: full-strength selection from the center out to innerWidth
  • Falloff zone: a smooth decline from innerWidth to outerWidth
  • Off region: no hue-band influence outside outerWidth

For example, if outerWidth = 45° and feather = 0.75, then innerWidth = 11.25°. That means the strongest influence is only near the selected hue center, while the adjustment continues to taper outward until it reaches ±45°.

9. Saturation Reliability

Low saturation makes hue unreliable because tiny RGB differences can produce unstable hue angles. The model therefore reduces trust in hue-band targeting as saturation falls. This prevents weak-color background and neutral structures from being pushed too aggressively by hue-specific controls.

10. Dark and Highlight Protection

Dark/background protection and highlight/star-core protection exist to keep the tool from behaving like an unrestricted global color rotator. Conceptually, these protections reduce adjustment weight in fragile areas such as near-black background or bright stellar cores, depending on mode and context.

11. Range Mask

leftRamp = smoothstep(low - feather, low, Y)
rightRamp = 1 - smoothstep(high, high + feather, Y)
rangeMask = clamp01(leftRamp * rightRamp)

Range Mask selects a luminance interval rather than a hue interval. Low/High define the main brightness window, and Feather softens the edges so targeted adjustments do not break abruptly.

12. Neutral / Low-Saturation Model

neutralMask = 1 - smoothstep(satStart, satFull, saturation)

This provides a luminance-focused path for weak-color pixels where hue is unreliable. It is especially relevant for background shaping, gray dust, and low-chroma structures. In this mode, hue radius does not apply.

13. Chroma-Vector Adjustment Concept

Conceptually, the tool separates a luminance-like component from chroma, scales saturation, rotates hue, adjusts luminance, then recombines and clamps to a valid RGB range. This should be understood as a practical nonlinear editing model, not a claim of perfect perceptual or physical color science.

14. Combined Mask

finalMask =
  hueMask *
  saturationReliability *
  darkProtection *
  highlightProtection *
  rangeMask

If additional pass-specific terms are applied in code, they conceptually sit on top of this structure. The practical behavior is that hue selection, reliability, protection, and luminance gating combine before the edit is applied.

15. Refinement Passes

working = original
for each enabled pass:
    working = applyPass(working, pass)

This supports workflows such as broad global color setup first, targeted background or halo cleanup later, and highlight- or luminance-specific work in a separate pass.

16. Preview and Diagnostics

Preview is based on downsampled image data for speed. Histogram uses preview luminance, the polar plot uses sampled preview pixels, the probe reads preview coordinates, and mask views represent preview-resolution selection behavior.

Final save operates on the full-resolution working image, which is why small local detail differences can exist even when the overall preview direction is accurate.

17. Adjustment Set JSON

Adjustment Set JSON stores the working state of the tool. This can include image type, sensitivity, pass ordering and enabled state, band values, hue radius and feather, Range Mask state, Neutral / Low-Saturation state, and related working settings.

The file is intended for repeatability and workflow continuity rather than for diagnostic rendering.

18. Browser and TIFF Considerations

  • memory usage matters for large images
  • TIFF import/export depends on the included browser-side TIFF I/O code
  • preview responsiveness may depend on browser performance and available RAM

The tool is designed to stay local and client-side, but large astrophotography files can still be demanding in a browser session.

19. Limitations

  • not intended for linear calibration
  • extreme changes can create artifacts
  • preview is approximate
  • hue is unreliable in neutral areas
  • Range Mask depends on the current stretch
  • saturated star cores require care
  • browser memory limits can constrain very large files

20. Practical Guidance

  • start with small adjustments
  • inspect masks before strong edits
  • create a new pass for targeted Range Mask work
  • use Stars Present when unsure
  • save Adjustment Sets for complex sessions

Astro Color Mixer Web works best when used deliberately, with the user checking both the visual preview and the diagnostic views before committing strong targeted changes.
